## 3. Análise por tabela

Legenda: **U** = usuário autenticado comum. "Telefone" = `telefone = current_setting('app.user_phone', true)`.

> **Observação geral sobre `app.user_phone`:** o navegador (supabase-js/PostgREST) **não consegue definir** essa variável de sessão. Sem ela, `current_setting(..., true)` devolve NULL/'' e todas as policies "Telefone" avaliam como falsas. Portanto, **com RLS ligado e só essas policies, U não lê nem escreve nada** (o painel quebra). O lado bom é que o padrão falha fechado. O lado ruim é que isso empurra o time para "consertos" perigosos (ver A1).

### 3.1 `perfis` (novo)

- **RLS ligado?** **Nenhum arquivo executa `ALTER TABLE public.perfis ENABLE ROW LEVEL SECURITY`** (`schema.sql`, `create_admin.sql`, `rls_policies.sql` e `finalzap_rls_policies.sql` não fazem isso).
- **Policies** (`rls_policies.sql`):
  - `"Users can view own profile"`: SELECT, `auth.uid() = auth_id OR telefone = app.user_phone`
  - `"Admins can manage profiles"`: ALL, `auth.role() = 'service_role'` (inútil, já que `service_role` ignora RLS)
- **Se o RLS estiver DESLIGADO (cenário dos arquivos):** `anon` e U fazem SELECT/INSERT/UPDATE/DELETE em todas as linhas. **Escalada de privilégio:** `PATCH /rest/v1/perfis?auth_id=eq.<meu-uid>` com `{"role":"admin"}` dá acesso ao painel admin (`AdminGuard` confia em `perfis.role`). Também é possível trocar `telefone`/`auth_id` e **sequestrar o telefone de outra pessoa**, passando a ver os dados financeiros dela, já que o front resolve o telefone por `perfis.auth_id`.
- **Se o RLS estiver LIGADO com essas 2 policies:** U só lê o próprio perfil e não consegue INSERT/UPDATE/DELETE (o ALL só vale para `service_role`). Não há escalada. Mesmo assim, faltam um `REVOKE UPDATE (role, telefone, auth_id)` como defesa em profundidade e um índice único em `auth_id`.
- **Severidade:** **Crítico (C2)** até ser confirmado que o RLS está ligado no banco real.

### 3.2 `assinaturas`

- **RLS ligado?** Sim em `finalzap_rls_policies.sql` e `finalzap_assinaturas.sql`. Não em `schema.sql`.
- **Policies:** `"Users can view own subscriptions"` (SELECT, Telefone), `"Users can insert own subscription"` (INSERT, Telefone), `"Users can update own subscription"` (UPDATE, Telefone, sem WITH CHECK; no Postgres o USING vira o check, então não dá para trocar o telefone para outro).
- **anon:** nada (falha fechado). **U:** nada pelo navegador (A1). Se `app.user_phone` passar a ser definível (RPC `set_config` ou JWT claim controlado pelo usuário), **U pode criar ou atualizar a própria assinatura com `status='Ativo'` e `data_vencimento` no futuro, liberando o produto pago sem pagar** (A2).
- **Ler assinaturas de outros:** as policies não permitem. Porém, `verificar_assinatura_ativa(p_telefone)` (INVOKER, então respeita RLS) e as funções DEFINER de outros arquivos não leem assinaturas diretamente. Sem vazamento direto.
- **Admin:** o painel admin (`cadastrar_assinatura`, `atualizar_assinatura`, `remover_assinatura` em `financeService.ts`) escreve direto do navegador, mas **não existe policy de admin**. O painel só funciona se o RLS estiver desligado, o que seria crítico. Não há policy de DELETE.

### 3.3 `movimentacoes`

- **RLS:** ligado em `finalzap_rls_policies.sql`/`finalzap_movimentacoes.sql` (este último está quebrado, ver A4).
- **Policies:** SELECT/INSERT/UPDATE por Telefone. Os nomes variam: `"Users can insert own movements"` (plural, em `rls_policies.sql`) vs `"Users can insert own movement"` (singular, nos demais). Assim, ambas podem coexistir: são duplicatas permissivas inofensivas, mas confusas. **Sem policy de DELETE** (o front não consegue excluir).
- **anon/U:** nada (A1). **Bypass via RPC:** `filtrar_movimentacoes_periodo(p_telefone, ...)` e `registrar_movimentacao(p_telefone, ...)` são `SECURITY DEFINER`, então qualquer pessoa lê ou escreve movimentações de qualquer telefone (C1).

### 3.4 `orcamentos`

- **RLS/policies:** SELECT/INSERT/UPDATE por Telefone, mesmo nome em 3 arquivos (A3). Sem DELETE.
- **Bypass:** `consultar_orcamento_mes` e `definir_orcamento` (DEFINER, telefone livre). Obs.: `finalzap_orcamentos.sql` tem `UNIQUE(...) WHERE` (sintaxe inválida) e `ON CONFLICT` com `mes` NULL nunca conflita.

### 3.5 `contas_a_pagar`

- **Policies:** `"Users can view own bills"`/`"insert"`/`"update"` (`rls_policies.sql`) + `"Users can view own accounts"` (SELECT) + `"Users can manage own accounts"` (ALL, `finalzap_rls_policies.sql`) + `"Users can manage their accounts"` (ALL, `finalzap_contas_a_pagar.sql`, arquivo inteiro comentado). Policies redundantes; `"Users can view own accounts"` aparece em 2 arquivos (erro 42710 se ambos rodarem).
- **Bypass:** `marcar_conta_paga_com_despesa(p_conta_id, p_telefone)` (DEFINER; exige conhecer o UUID da conta, mas não verifica se o chamador é o dono), `cadastrar_conta_a_pagar`, `consultar_contas_a_pagar`, `marcar_conta_como_paga(p_telefone, ...)` (**marca TODAS as contas pendentes do telefone como pagas**; tem erro de sintaxe, então provavelmente não existe).

### 3.6 `lancamentos_recorrentes`

- **Policies:** SELECT/INSERT/UPDATE (`rls_policies.sql`) + SELECT/ALL (`finalzap_rls_policies.sql`). `"Users can view own recurrences"` está duplicada (A3).
- **Bypass:** `inserir_lancamento_recorrente`, `listar_proximos_lancamentos` (DEFINER, telefone livre).

### 3.7 `logs_lembrete`

- **Policies:** `"Users can view own reminder logs"` / `"Users can view own logs"` (SELECT, Telefone) e **`"System can insert logs"` FOR INSERT WITH CHECK (TRUE)**, sem `TO`, ou seja, vale para `anon`.
- **anon:** **pode inserir logs falsos para qualquer telefone** (A5). Isso polui a auditoria e pode suprimir lembretes, caso o n8n use o log para deduplicar. O backend usa `service_role`, que ignora RLS, então essa policy não é necessária.
- **Bypass:** `registrar_lembrete` (DEFINER).

### 3.8 `custos_fixos` e `uso_servico` (não existem no banco real)

- Policies por Telefone com SELECT/INSERT(/UPDATE). Conceitualmente errado: são **custos do negócio e consumo de tokens**, usados pelo painel admin. Deveriam ser **somente admin**. Do jeito que está, U poderia inserir uso/custo "próprio" e o admin não enxerga nada (M2).

### 3.9 `hotmart_eventos` (não existe no banco real)

- RLS ligado, **nenhuma policy**, então só `service_role` acessa. **Correto.** Recomendado também `REVOKE ALL ... FROM anon, authenticated`. As colunas novas de `assinaturas` herdam as policies da tabela.

### 3.10 `whatsapp_sessions` / `whatsapp_instances` (antigo)

- `whatsapp_sessions`: RLS ligado; policy `whatsapp_sessions_service_role` (`schema.sql`) **e** `whatsapp_sessions_service_role_all` (migration), ambas `auth.role() = 'service_role'`. Na prática ninguém além do `service_role` acessa, o que é **correto**, mas as policies são redundantes. **A tabela guarda chaves de sessão do Baileys:** nunca crie policy para `authenticated`.
- `whatsapp_instances`: `auth.uid() = user_id` (ALL em `schema.sql`; 4 policies por comando na migration). Correto. Duplicação de policies inofensiva.

### 3.11 Tabelas antigas (`profiles`, `categories`, `accounts`, `transactions`, `fixed_transactions`, `investments`, `budgets`, `savings_*`, `credit_cards`, `pluggy_*`, `transacoes`)

- Todas com RLS ligado e `auth.uid() = user_id/id`. **Modelo correto.**
- `profiles`: `"Users can update own profile"` sem restrição de coluna, então U altera `n8n_webhook_url`. Se o backend chama essa URL, há risco de SSRF ou desvio de dados (M4).
- `schema.sql` e `migrations/` criam as mesmas policies (`"Users can read own profile"`, `"Users can manage own categories"`, storage, etc.). Rodar os dois dá erro 42710 (A3).

## 4. Achados detalhados

### C1 — Funções `SECURITY DEFINER` com telefone livre, executáveis por `anon` (Crítico)

Nenhum arquivo faz `REVOKE EXECUTE`. No Supabase, funções novas em `public` recebem `EXECUTE` para `PUBLIC`/`anon`/`authenticated`, e todas ficam expostas em `/rest/v1/rpc/*`. Funções DEFINER rodam como dono (ignoram RLS):

| Função | Arquivo | Efeito para quem chama (inclusive anon) |
|---|---|---|
| `marcar_conta_paga_com_despesa(p_conta_id, p_telefone)` | `schema.sql`, `finalzap_functions.sql` | marca a conta de outro como paga e cria despesa (precisa do UUID da conta) |
| `filtrar_movimentacoes_periodo(p_telefone, ...)` | `finalzap_functions.sql` | **lê todas as movimentações de qualquer telefone** (enumerável) |
| `registrar_movimentacao(p_telefone, ...)` | `finalzap_movimentacoes.sql` | insere receita/despesa em nome de qualquer telefone |
| `consultar_orcamento_mes` / `definir_orcamento` | `finalzap_orcamentos.sql` | lê/altera orçamento de terceiros |
| `cadastrar_conta_a_pagar` / `consultar_contas_a_pagar` / `marcar_conta_como_paga` | `finalzap_contas_a_pagar.sql` | cria/lê/quita contas de terceiros (arquivo inteiro comentado) |
| `inserir_lancamento_recorrente` / `listar_proximos_lancamentos` | `finalzap_lancamentos_recorrentes.sql` | idem (arquivo inteiro comentado) |
| `registrar_lembrete` | `finalzap_logs_lembrete.sql` | forja logs (arquivo inteiro comentado) |
| `obter_dados_usuario(p_telefone)` | `finalzap_functions.sql` | vazaria dados de `profiles` (falha em runtime: `profiles.telefone` não existe) |
| `consultar_saldo_por_usuario(p_telefone)` | `finalzap_functions.sql` | vazaria saldo (falha em runtime: `accounts.telefone` não existe) |

Nenhuma tem `SET search_path`. Prova de conceito (não executada): `POST /rest/v1/rpc/filtrar_movimentacoes_periodo {"p_telefone":"55119...","p_mes_inicial":"2000-01"}` só com a chave anon.
**Correção:** revogar EXECUTE de `PUBLIC/anon`. Funções que o n8n usa devem ser chamadas com `service_role`. A única que o front usa (`marcar_conta_paga_com_despesa`) deve derivar o telefone de `auth.uid()` (ver seção 7).

### C2 — `perfis` sem RLS habilitado nos scripts (Crítico, potencial)

Ver 3.1. Impacto se estiver desligado: leitura de todos os perfis (nome, e-mail, telefone), autopromoção para admin e sequestro de telefone. Confirme com a consulta 6.1.

### C3 — `schema.sql` não habilita RLS em nenhuma tabela (Crítico, potencial)

`schema.sql` cria as 7 tabelas sem `ENABLE ROW LEVEL SECURITY`, e `rls_policies.sql` só cria policies. Quem rodar apenas esses dois arquivos (o par "natural") fica com **policies inertes e as tabelas abertas para `anon`**. O RLS só é ligado em `finalzap_rls_policies.sql`, que por sua vez **falha** se rodar depois de `rls_policies.sql` (A3). Pode facilmente ter sido abortado no meio.

### C4 — Credenciais versionadas (Crítico, fora de RLS mas encontrado durante a leitura)

- `finalzap/create_admin.sql` (comentário da linha 45): senha do admin em texto puro.
- `WhatsApp-Fin/supabase/schema.sql` (linhas 580-657): e-mail e senha em texto puro de um usuário real, além de inserção direta em `auth.users`.
**Ação:** trocar essas senhas já, remover dos arquivos e do histórico, e nunca semear `auth.users` por SQL versionado. Os valores não são reproduzidos neste relatório.

### A1 — Conflito `app.user_phone` × `auth.uid()` (Alto, de arquitetura)

- O front autentica com Supabase Auth (JWT com `sub = auth.uid()`). O PostgREST não deixa o cliente definir GUCs arbitrários. `app.user_phone` só pode ser definido por (a) conexão direta ao Postgres (n8n/backend) ou (b) uma RPC que chame `set_config`.
- Consequências:
  1. Com RLS ligado, **todas as tabelas por telefone retornam vazio para o painel**. O `.eq('telefone', t)` do front é só filtro, não segurança.
  2. A "solução" (b) é um **bypass total**, porque o usuário passaria qualquer telefone. Uma policy `USING (true)` "para destravar" seria o mesmo desastre.
  3. O n8n/backend usa `service_role`, que já ignora RLS, então o `app.user_phone` não protege nada lá também. **O mecanismo não tem utilidade em nenhum dos dois lados.**
- **Correção:** derivar o telefone **no servidor** a partir do JWT, com uma função `current_user_phone()` (`SECURITY DEFINER`, `STABLE`) que lê `perfis.telefone WHERE auth_id = auth.uid()`, e usá-la nas policies. Isso exige que `perfis.telefone`/`auth_id` sejam **imutáveis para o usuário** (só admin/service_role altera). Médio prazo: adicionar `user_id uuid` às tabelas financeiras e isolar por `auth.uid()`, como nas tabelas antigas.

### A2 — Usuário pode "se dar" assinatura ativa (Alto)

Policies de INSERT/UPDATE em `assinaturas` para o próprio telefone. `assinaturas` é o controle de acesso pago (Hotmart), então só webhook/backend/admin deveriam escrever.

### A4 — Arquivos `finalzap_*.sql` corrompidos (Alto, operacional)

`finalzap_movimentacoes.sql`, `finalzap_orcamentos.sql` (linha 5), `finalzap_contas_a_pagar.sql`, `finalzap_lancamentos_recorrentes.sql` e `finalzap_logs_lembrete.sql` contêm `\n` **literal** dentro de uma linha `--`. Todo o conteúdo seguinte na linha vira comentário:
- `contas_a_pagar`, `lancamentos_recorrentes` e `logs_lembrete`: **o arquivo inteiro é um comentário** (não cria tabela, RLS, policy nem função).
- `movimentacoes` e `orcamentos`: o início do `CREATE TABLE` é comentado e a linha seguinte dá **erro de sintaxe**.
O banco real tem colunas que só existem nesses arquivos (ex.: `logs_lembrete.tipo_lembrete`), então alguém aplicou uma versão diferente da versionada. **O repositório não descreve o banco real** (ver B4).

### A5 — `logs_lembrete`: INSERT aberto a todos (Alto/Médio)

`WITH CHECK (TRUE)` sem `TO`: `anon` pode inserir. Remover a policy (o backend usa `service_role`).

### M1 — Sem GRANT/REVOKE

Nenhum arquivo contém `GRANT`/`REVOKE`. Valem os privilégios padrão do Supabase (`anon` e `authenticated` com ALL em tabelas/sequences de `public` e EXECUTE em funções). **O RLS é a única barreira**, então qualquer tabela com RLS desligado fica totalmente aberta.

### M2–M5, B1–B4

- **M2:** `custos_fixos` e `uso_servico` deveriam ser só admin.
- **M3:** `seed_default_categories(p_user_id uuid)` é DEFINER e executável por `anon`, permitindo injetar 7 categorias em qualquer conta (o UUID é necessário). Revogar EXECUTE (só o trigger precisa dela).
- **M4:** `profiles` antigo: limitar as colunas atualizáveis (`n8n_webhook_url` não deveria ser editável pelo usuário, ou deveria ser validado).
- **M5:** policies sem `TO authenticated` também são avaliadas para `anon`. `auth.role()` está obsoleto. Em policies prefira `(select auth.uid())` (performance: initPlan).
- **B1:** nenhuma função tem `SET search_path = ''`.
- **B2:** `"Public avatar read"` em `storage.objects` permite listar o bucket. Um bucket público não precisa de policy SELECT para servir arquivos por URL.
- **B3:** policies `auth.role() = 'service_role'` são redundantes (`service_role` tem BYPASSRLS).
- **B4:** banco real diverge dos arquivos: `hotmart_eventos`, `custos_fixos` e `uso_servico` não existem; `assinaturas` sem colunas Hotmart; `contas_a_pagar` sem `lembrete_enviado_em`. A migration `20261116000003_hotmart.sql` está pendente.

## 7. Proposta de policies corretas (TEXTO, não aplicado)

Premissas: o painel usa Supabase Auth (`auth.uid()`); o n8n/webhook Hotmart usam `service_role` (ignora RLS); `perfis.auth_id` liga o usuário ao telefone. Script idempotente, para rodar **uma única vez** depois de corrigir os arquivos A4 e **substituir** `rls_policies.sql` e `finalzap_rls_policies.sql`.

begin;

-- ============================================================
-- 0. Funções auxiliares (telefone e admin derivados do JWT)
-- ============================================================
create unique index if not exists perfis_auth_id_uniq on public.perfis(auth_id) where auth_id is not null;

create or replace function public.current_user_phone()
returns text language sql stable security definer set search_path = '' as $$
  select p.telefone from public.perfis p where p.auth_id = (select auth.uid())
$$;

create or replace function public.is_admin()
returns boolean language sql stable security definer set search_path = '' as $$
  select exists (select 1 from public.perfis p
                 where p.auth_id = (select auth.uid()) and p.role = 'admin')
$$;

-- ============================================================
-- 1. Fechar EXECUTE padrão (C1, M3) e reabrir só o necessário
-- ============================================================
revoke execute on all functions in schema public from public, anon, authenticated;
alter default privileges in schema public revoke execute on functions from public, anon, authenticated;

grant execute on function public.current_user_phone() to authenticated;
grant execute on function public.is_admin()           to authenticated;

-- Funções que só o n8n usa (registrar_movimentacao, definir_orcamento, filtrar_movimentacoes_periodo,
-- cadastrar_conta_a_pagar, registrar_lembrete, inserir_lancamento_recorrente, ...):
-- ficam SEM grant (o n8n chama com service_role). Ideal: movê-las para um schema não exposto (ex.: "private").

-- Única RPC do front: o telefone vem do JWT; o parâmetro é mantido só por compatibilidade
create or replace function public.marcar_conta_paga_com_despesa(p_conta_id uuid, p_telefone text default null)
returns json language plpgsql security definer set search_path = '' as $$
declare
  v_tel  text := public.current_user_phone();
  v_conta public.contas_a_pagar%rowtype;
  v_mov  uuid;
begin
  if v_tel is null then raise exception 'não autenticado' using errcode = '42501'; end if;
  if p_telefone is not null and p_telefone <> v_tel then
    raise exception 'telefone não pertence ao usuário' using errcode = '42501';
  end if;

  select * into v_conta from public.contas_a_pagar
   where id = p_conta_id and telefone = v_tel for update;
  if not found then return json_build_object('success', false, 'error', 'Conta não encontrada'); end if;
  if v_conta.status = 'paga' then
    return json_build_object('success', true, 'message', 'Conta já estava paga', 'movimentacao_id', v_conta.movimentacao_id);
  end if;

  insert into public.movimentacoes (telefone, tipo, valor, categoria, descricao, data, mes, fonte, idempotency_key)
  values (v_tel, 'despesa', v_conta.valor, coalesce(v_conta.categoria, 'Contas'), v_conta.descricao,
          current_date, to_char(current_date, 'YYYY-MM'), 'conta_paga', 'conta_' || v_conta.id)
  on conflict (idempotency_key) do nothing
  returning id into v_mov;

  update public.contas_a_pagar set status = 'paga', pago_em = current_date, movimentacao_id = v_mov
   where id = p_conta_id;
  return json_build_object('success', true, 'message', 'Conta marcada como paga', 'movimentacao_id', v_mov);
end $$;
revoke execute on function public.marcar_conta_paga_com_despesa(uuid, text) from public, anon;
grant  execute on function public.marcar_conta_paga_com_despesa(uuid, text) to authenticated;

-- ============================================================
-- 2. Limpar TODAS as policies antigas das tabelas do FINALZAP (A3)
-- ============================================================
do $$
declare r record;
begin
  for r in select tablename, policyname from pg_policies
           where schemaname = 'public'
             and tablename in ('perfis','assinaturas','movimentacoes','orcamentos','contas_a_pagar',
                               'lancamentos_recorrentes','logs_lembrete','custos_fixos','uso_servico',
                               'hotmart_eventos','whatsapp_sessions','whatsapp_instances')

  end loop;
end $$;

-- 3. perfis — ler o próprio (admin lê todos); usuário só edita nome/e-mail (C2)
-- ============================================================

revoke all on public.perfis from anon, authenticated;
grant select on public.perfis to authenticated;
grant update (nome, email) on public.perfis to authenticated;   -- role/telefone/auth_id: só service_role

                     with check (telefone = (select public.current_user_phone()))$p$, t || '_update_own', t);

end $$;
